# 승인 체크리스트 v1 · 2회차

> **오늘 바뀐 점**
> 1. '충분한가 · 적절한가 · 심각한 문제' 같은 판단어를 지우고, 모든 항목을 예/아니오 질문으로 바꿨다.
> 2. 새 public 메서드 · 엔드포인트에는 테스트가 있어야 승인한다(접근자 제외).
> 3. 치명 4종 · 컨벤션 반려 4종을 못 박고, 범위 밖 변경은 같은 파일 안 import 정리만 허용한다.

버전: v1 · 2회차 (우리 팀 초안). 팀원들의 초안과는 3회차 시작 때 맞춰 본다.
AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다.
모든 항목은 **"예"가 통과**다. 한 기준 안의 항목이 모두 "예"이면 그 기준은 충족이다. 네 기준이 **모두** 충족되어야 승인이고, 하나라도 미충족이면 반려다. "확인 필요"가 남은 기준이 있으면 승인하지 않고 사람에게 확인을 요청한다.

## 심각도 정의

- **치명** — 기준 2 의 네 항목 중 하나라도 "아니오". 1건이라도 있으면 반려.
- **경고** — 판정에 반영하지 않고 기록만 한다. 대상: 입력 검증 누락, catch 에서 로그 없이 다른 예외로 바꿔 던짐, N+1 쿼리, 네이밍, `@DisplayName` 누락, 중복 코드, 그 밖의 `CLAUDE.md` 컨벤션 위반.
- **제안** — 더 나은 방법이 있다는 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 변경된 모듈의 테스트 명령을 실제로 실행했는가? (실행하지 않았으면 "확인 필요")
- [ ] 실행 결과에서 실패 · 오류가 0건인가?
- [ ] 새로 추가된 public 메서드 · 엔드포인트마다, 그것을 직접 호출하는 테스트가 1개 이상 있는가? (getter · setter · 생성자 · record 접근자는 제외)
- [ ] 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 없는가?

## 2. 치명 이슈 0건

- [ ] 비밀번호 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처에 리터럴로 들어 있지 않은가? (`app-pass` 같은 실습용 더미 값은 예외)
- [ ] 데이터를 지우거나 덮어쓰는 코드가 새로 생겼다면, 그 내용이 요청 문장에 적혀 있는가? (새로 생기지 않았으면 "예")
- [ ] 인증 · 권한 검사를 건너뛰는 경로가 새로 생기지 않았는가?
- [ ] SQL 을 문자열로 이어 붙여 만드는 곳이 없는가? (파라미터 바인딩 사용)

## 3. 요청 범위 이탈 없음

- [ ] 요청 문장이 한 문장으로 확인되었는가? (아니면 판정하지 않고 먼저 묻는다)
- [ ] 변경 파일마다 요청 문장으로 바뀐 이유를 댈 수 있는가?
- [ ] 요청 밖 변경이 "요청으로 바뀐 파일 안의 import 정리"뿐인가? (요청 밖 변경이 없으면 "예")
- [ ] 의존성 추가 · DB 스키마 변경 · 설정 파일 변경이 있다면 요청 문장에 적혀 있는가? (없으면 "예")

## 4. 컨벤션 준수

- [ ] 컨트롤러가 Repository 를 주입받거나 SQL 을 직접 실행하지 않는가?
- [ ] 다른 도메인의 Repository 를 직접 주입하지 않는가?
- [ ] 빈 `catch` 블록이 없는가?
- [ ] `System.out` · `System.err` · `printStackTrace()` · `console.log` 가 남아 있지 않은가?

위 네 항목 밖의 `CLAUDE.md` 컨벤션 위반은 '경고'로 기록한다(`convention-check` Skill 이 있으면 그 결과를 쓴다).

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 · 확인 필요 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 코드는 수정하지 않는다.

# 레거시 모듈 문서화

대상 모듈(legacy 하위 경로, 범위 제한 있으면 그 안에서만)을 읽고 인수인계용 문서 3종을 만든다.

**읽기 전용**: 분석 대상 폴더(`legacy/...`) 안의 파일은 읽기만 한다. 수정 · 포맷팅 · 리팩터링하지 않는다.

## 모듈명 매핑

산출물 경로의 `<모듈명>`은 폴더 이름이 아니라 다음 중 하나다:
`legacy/item-bank-php` → `item-bank`, `legacy/assignment-thymeleaf` → `assignment`, `legacy/grade-mssql` → `grade`.
목록에 없는 경로가 주어지면 진행 전에 사용자에게 매핑을 묻는다.

## 절차

각 단계가 끝나면 결과를 해당 파일에 저장한 뒤 다음 단계로 넘어간다. 이전 단계 산출물을 다음 단계가 참고 자료로 삼는다(각 문서 상단에 "먼저 읽음" 목록으로 명시).

1. **계획 제시**: 무엇을 읽을지(파일 목록 · 순서), 범위 제한이 있으면 그 경계를 먼저 한 문단으로 제시하고 진행한다.
2. **진입점**: 웹/배치 진입점 파일, 각 파일의 역할 · HTTP 메서드 · require·import 의존을 표로 정리 → `docs/<모듈명>/ARCHITECTURE.md`의 "진입점 표" 절에 저장.
3. **의존 관계**: 파일 간 include/require·클래스 의존을 mermaid `flowchart`로 그림 → 같은 문서의 "의존 관계" 절에 저장.
4. **데이터 흐름**: 각 진입점 안에서 함수 호출 · 분기 · DB 접근이 이어지는 흐름을 mermaid `flowchart`로 그리고, DB 호출 표(파일:함수 / 대상 테이블·뷰 / 종류 / 근거)를 작성 → 같은 문서의 "파일별 기능 흐름"·"DB 호출 표" 절에 저장. 여기서 확인한 테이블 · 컬럼 · 관계를 `docs/<모듈명>/ERD.md`(mermaid `erDiagram` + 테이블 목록 표)로 정리해 저장한다.
5. **비즈니스 규칙 후보**: 코드의 조건문 · SQL로 직접 확인되는 규칙만 추출해 `docs/<모듈명>/BUSINESS-RULES.md`에 저장(형식은 아래). 주석에만 있고 코드로 확인 안 되는 내용은 규칙으로 올리지 않고 비고에 "주석만 있음"으로 남긴다. 주석과 코드가 다르면 코드를 기준으로 쓰고 차이를 비고에 남긴다. 매직 넘버는 별도 표로 모은다.

각 단계 · 각 문서에서 실제로 읽지 못했거나 판단을 보류한 부분은 "미확인 목록"에 남긴다. 추측은 반드시 "(추정)"으로 표시한다.

## 규칙 형식

BUSINESS-RULES.md의 각 규칙은 다음 항목을 그대로 넣는다:

- **규칙**: 한 문장
- **근거**: 파일:줄번호
- **근거 코드**: 실제 코드 인용(짧게)
- **확신도**: 확실 / 추정
- **비고**: 매직 넘버·주석 불일치·미확인 사항 등

## 하지 말 것

- 존재하지 않는 함수 · 클래스를 근거로 인용하지 않는다. 인용 전에 실제로 그 줄을 읽었는지 확인한다.
- 호출 방향을 추측으로 뒤집지 않는다(A가 B를 부르는지, B가 A를 부르는지는 코드에서 직접 확인).
- 코드에 없는 규칙을 "당연히 있을 법한 것"으로 창작하지 않는다 — 없으면 "이 모듈에 없음"이라고 명시한다.
- 조건이 여러 개 함께 걸리는 로직(검색 필터 조합 등)은 조건 하나씩만 보고 규칙을 적지 말고, 조건들을 이어붙이는 코드(`WHERE`/`if` 조립부) 전체를 직접 봐서 결합 방식(AND/OR)까지 확인한다.
- 같은 데이터에 접근하는 경로가 여러 개면(예: 목록 조회와 건수 조회) 근거를 그중 하나만 인용하지 말고 모든 경로의 코드를 확인해 근거에 포함한다.

## 마무리: 사람 표본 점검 추천

BUSINESS-RULES.md 끝에 "사람이 표본 점검할 규칙 3개 추천" 절을 추가한다. 확신도가 낮거나, 주석과 코드가 다르거나, 비즈니스적으로 영향이 큰 규칙 중에서 고르되 **가장 그럴듯해 보이는(확신도 "확실"로 적었지만 파급력이 큰) 규칙을 최소 1개 포함**한다. 각 항목에 왜 점검이 필요한지 한 줄로 적는다.

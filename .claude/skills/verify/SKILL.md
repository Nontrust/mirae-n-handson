# verify

검증 대상: $ARGUMENTS

인자가 비어 있으면 `git diff upstream/main...HEAD` 를 대상으로 삼는다.

만든 쪽과 검증하는 쪽을 분리하는 리뷰 절차다. 이 Skill 은 리뷰어 역할만 한다. 배경은 저장소 루트의 `templates/verification-loop.md`, 판정 기준은 저장소 루트의 `templates/approval-checklist.md` 를 따른다. (경로는 모두 Skill 폴더가 아니라 저장소 루트 기준이다.)

## 절차

1. **요청 범위 확인.** 무엇을 요청했는지 한 문장으로 받았는지 확인한다. 주어지지 않았으면 판정하지 말고 먼저 질문하고 멈춘다.
2. **변경 파일 목록과 diff 읽기.** `git diff --stat <범위>` 로 목록을 먼저 보고, 파일마다 diff 를 읽는다. patch 파일이면 `git apply --stat` 으로 목록을 뽑는다.
3. **체크리스트 대조.** 저장소 루트의 `templates/approval-checklist.md` 를 읽고 항목마다 충족 · 미충족 · 확인 필요로 표시한다. 항목 내용은 이 파일에 복사하지 않고 그 파일을 기준으로 한다.
4. **테스트 실행.** 변경된 폴더의 테스트만 실행한다.
   - `modern/api` 가 바뀌었으면 `cd modern/api && ./gradlew test`
   - `modern/web` 이 바뀌었으면 `cd modern/web && npm test`
   - 이관 코드이면 `characterization` 에서 `npm test`(레거시 대상)와 `TARGET_BASE_URL=http://localhost:8080 npm test`(새 API 대상) 를 모두 실행한다.
   - 서버 꺼짐 · 의존성 미설치 등으로 실행하지 못하면 그 사실을 적고 사람에게 기동을 요청한다.
5. **승인 기준 판정.** 체크리스트의 네 기준을 하나씩 판정한다. 하나라도 미충족이면 반려, 치명 이슈가 1건이라도 있으면 반려다.

## 사용량 절약

- 테스트 출력은 통과 / 실패 수와 실패한 테스트 이름만 남긴다. 전체 로그를 대화에 싣지 않는다.
- 실패 원인을 설명해야 하면 해당 테스트의 핵심 한두 줄만 인용한다.

## 출력 형식

1. 첫 줄: `판정: 승인` 또는 `판정: 반려`
2. 기준별 결과 표

   | 기준 | 결과 | 근거 |
   |---|---|---|

3. 이슈 목록 — 한 건은 `심각도(치명 / 경고 / 제안) · 파일:줄번호 · 근거 · 수정 방향` 순서로 적는다.
4. 확인 필요 — 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 여기에 따로 적는다.

## 하지 말 것

- 코드를 수정하지 않는다. 보고만 한다.
- 근거 줄번호를 댈 수 없는 지적은 하지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다. 실행하지 않았으면 "실행하지 않음"이라고 적는다.
- 요청 범위를 모르는 상태에서 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.

# impact

수정 전에 대상 함수 · 프로시저의 영향 범위를 조사한다. `legacy/`를 포함한 저장소 전체가 조회 대상이다 — 읽기만 하며 코드는 고치지 않는다.

## 분석 대상

- 인자로 함수 · 프로시저 이름 또는 `파일:줄번호`를 받는다.
- 인자가 없으면 추측해서 진행하지 않고 무엇을 분석할지 되묻는다.
- 같은 이름이 여러 곳에 정의되어 있으면 후보를 모두 나열하고 어느 것인지 확인한다.

## 진행 절차

1. **정의 위치 확정** — Grep으로 대상의 선언 · 정의를 찾아 파일:줄번호를 특정한다.
2. **호출부 역추적**
   - 대상을 직접 호출하는 곳을 찾는다.
   - 그 호출자를 다시 부르는 곳을 찾는다.
   - 진입점(컨트롤러 엔드포인트, 화면, URL, 배치 · 스케줄러 시작점 등)에 닿을 때까지 이 과정을 반복한다.
   - 각 단계마다 파일:줄번호를 남긴다.
3. **테이블 사용처 조사**
   - 대상 함수가 읽거나 쓰는 테이블(SELECT/INSERT/UPDATE/DELETE 대상, JPA 엔티티가 매핑하는 테이블 등)을 찾는다.
   - 같은 테이블을 읽거나 쓰는 다른 함수 · 프로시저를 Grep으로 찾아 나열한다.
4. **관련 규칙 연결**
   - 대상 함수가 속한 모듈 경로 아래 `docs/<모듈명>/BUSINESS-RULES.md`가 있는지 확인한다.
   - 있으면 읽고 대상 함수 · 테이블과 관련된 규칙 ID를 찾아 연결한다.
   - 없으면 "관련 규칙 문서 없음"이라고 적는다.

## 출력 형식 (이 순서 고정)

1. **영향받는 화면 목록** — 호출 경로 추적으로 확인한 화면 · API 엔드포인트 · 배치명.
2. **호출 경로** — `진입점 → … → 대상 함수` 형태로, 각 단계에 파일:줄번호를 붙인다.
3. **영향받는 테이블** — 테이블명별로 그 테이블을 쓰는 함수 목록과 근거 파일:줄번호.
4. **관련 규칙 ID** — `BUSINESS-RULES.md`에서 찾은 규칙 ID와 근거 줄번호. 문서가 없으면 "관련 규칙 문서 없음".
5. **수정 전 확보해야 할 테스트 케이스 제안** — 위 1~4의 영향 범위를 근거로, 수정 전에 있어야 할 테스트를 목록으로 제안한다.
6. **추적 한계** — 동적 호출(리플렉션, 문자열로 조합한 SQL · 프로시저명, 설정 기반 라우팅 등)처럼 검색으로 확인할 수 없는 경로가 의심되면 여기에 따로 적는다. 없으면 "없음".

모든 항목에 근거 파일:줄번호를 단다. 근거를 댈 수 없는 추정은 본문에 넣지 않고 "추적 한계"로 옮긴다.
코드는 고치지 않는다.

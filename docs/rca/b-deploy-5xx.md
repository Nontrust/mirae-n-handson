# b-deploy-5xx 장애 원인 분석

## 1. 수집 범위

원인 추측은 하지 않는다. 이 절은 어떤 구간의 로그를 볼지만 정한다. 파일은 통째로 읽지 않고 `wc` · `head` · `tail` · `grep` · `awk` 집계로만 확인했다.

### 1.1 파일별 개요

| 파일 | 줄 수 | 기록 기간 (KST) | 시각 형식 | 타임존 |
|---|---|---|---|---|
| `app.log` | 2,938 | 2026-09-17 09:00:04 ~ 14:39:57 | ISO 8601 (`2026-09-17T09:00:04.878+09:00`) | +09:00 (KST). 타임스탬프가 있는 1,275줄 모두 +09:00 |
| `nginx-access.log` | 20,365 | 2026-09-17 09:00:00 ~ 14:39:58 | nginx combined (`[17/Sep/2026:09:00:00 +0900]`) | +0900 (KST). 전체 줄 일치 |
| `deploy-history.md` | 39 | 2026-09-01 ~ 2026-09-17 (배포 이력) | `YYYY-MM-DD HH:MM:SS` (표) | 문서에 "모두 KST"로 명시 |

- `app.log`의 1,663줄은 타임스탬프가 없는 스택 트레이스 연속 줄이다. 시각 기준 집계에서는 제외했다.
- **KST 변환 규칙**: 세 파일 모두 KST이므로 변환이 필요 없다. 외부 도구(UTC 기준 모니터링 등)의 시각을 대조할 때만 UTC+9로 계산한다. 단, `deploy-history.md`는 문서 머리말의 선언에만 근거하며 파일 안에서 검증할 수 없다.
- `app.log` 줄에는 `HH:MM` 이하 밀리초가 있고 nginx는 초 단위다. 두 로그를 맞출 때는 분 단위로 비교하고, 필요하면 초 단위로 좁힌다.

### 1.2 오류 · 경고 · 5xx · 타임아웃 건수

집계 기준: `app.log`는 `ERROR` · `WARN` 레벨 줄, `nginx-access.log`는 상태 코드 5xx. `timeout` · `timed out` 문자열은 `app.log`에서 0건이다. nginx 로그에는 응답 시간 필드가 없어 타임아웃은 상태 코드(504 등)로만 볼 수 있는데, 504는 0건이다.

| 구분 | 건수 |
|---|---|
| `app.log` ERROR | 46 |
| `app.log` WARN | 35 |
| nginx 500 | 46 (`app.log` ERROR와 건수 일치) |
| nginx 502 | 8 |
| nginx 504 / 타임아웃 문자열 | 0 / 0 |
| (참고) nginx 404 / 409 / 400 | 969 / 35 / 29 — 5xx가 아니므로 구간 판단에서 제외 |

**분 단위 5xx (nginx)**

| 시각 | 분당 5xx | 상태 |
|---|---|---|
| 09:52 | 3 | 500 |
| 10:31 | 1 | 500 |
| 11:17 / 11:18 | 1 / 2 | 500 |
| 13:41 | 8 | 502 (13:41:51 ~ 13:41:59) |
| 13:46, 13:47 | 2, 1 | 500 |
| 13:50, 13:52, 13:53, 13:55, 13:58 | 4, 1, 1, 3, 2 | 500 |
| 14:02, 14:03, 14:06, 14:11 | 2, 4, 1, 3 | 500 |
| 14:15, 14:16, 14:22, 14:27, 14:28 | 1, 2, 3, 2, 1 | 500 |
| 14:31, 14:32, 14:34 | 2, 1, 3 | 500 (마지막 5xx 14:34:45) |

그 외 분은 모두 0건이다. `app.log` ERROR의 분 단위 분포는 위 500과 같은 분에 같은 건수로 나타난다. WARN은 하루 종일 분당 0~2건으로 흩어져 있고(09:06 ~ 14:35), 구간별로 뚜렷한 증가가 없다.

### 1.3 평소 수준과 달라지는 구간

- **평소 수준 (13:40 이전)**: 5xx는 4시간 40분 동안 7건(09:52 3건, 10:31 1건, 11:17 ~ 11:18 3건)이고 모두 분당 1~3건의 단발이다. 13:19 ~ 13:40에는 0건이다. 시간당 요청 수는 3,200 ~ 3,800건이다.
- **변화 시작**: 두 개의 시점이 있다.
  - **13:41:51** — 502 8건이 13:41:51 ~ 13:41:59에 몰려 있다. `app.log`에 13:41:48 graceful shutdown, 13:41:55 기동 시작, 13:42:00 `Started ... v1.4.2`가 기록돼 있어 v1.4.2 재기동 시각과 겹친다. 사실 확인까지만 하고 해석은 하지 않는다.
  - **13:46:38** — 이후 500이 반복된다. 13:46 ~ 14:34 사이 49분 중 24개 분에서 발생하고, 분당 1~4건이다.
- **변화 끝**: 마지막 5xx는 14:34:45이다. 다만 로그가 14:39:58에서 끝나므로 5분 동안 오류가 없었다는 것만 알 수 있고, 장애가 끝났다고 단정할 수 없다.
- **500의 공통 요청**: 500 46건 중 POST `/api/distributions/{41,42,43}/redistribute`가 45건이고, GET `/api/distributions/41`이 1건이다. 이 목록은 사실 기록이며 원인 판단이 아니다.
- **배포 시각 (참고)**: v1.4.2 배포 시작 13:40:05, 완료 13:42:31 (`deploy-history.md`).

### 1.4 제안 수집 구간

| 항목 | 제안 | 근거 |
|---|---|---|
| 핵심 구간 | 13:40:05 ~ 14:34:45 | 배포 시작 ~ 마지막 5xx |
| 시작 (앞 여유) | **13:10** (배포 시작 30분 전) | 기준선과 달라지는 첫 신호를 놓치지 않으려고 앞쪽을 넉넉히 둔다. 배포 전 변경 · 선행 증상을 확인하는 구간이다 |
| 끝 (뒤 여유) | **14:45** (마지막 5xx 10분 후) | 로그 끝(14:39:58) 이후 자료가 없어 수집만으로는 장애 종료를 확인할 수 없다. 14:39 이후 로그를 추가로 받아 ~ 15:00까지 늘리는 것을 권한다 |
| 여유 비율 | 앞 30분 : 뒤 10분 | 원인은 결과보다 앞에서 만들어지므로 앞을 3배로 둔다 |
| 별도 기준선 | 09:00 ~ 13:10 | 평소 5xx(7건)와 WARN 분포를 비교하는 용도. 전체 분석에는 쓰지 않고 집계만 참고한다 |

### 1.5 확인 필요 · 후속 요청

- 14:39:58 이후의 `app.log` · `nginx-access.log` (장애 종료 확인).
- `api-2` (10.20.1.22) 로그 유무. 이번 자료는 `api-1` 기준으로 보이나 파일 안에 호스트 표시가 없어 확인이 필요하다.
- 09:52 ~ 11:18의 사전 500 7건은 스택 트레이스가 배포 후 오류와 다르다(`loadOrThrow` 계열). 이번 장애와 같은 건인지는 판단하지 않고 기준선 항목으로만 둔다.
- `deploy-history.md`의 "배포 명령"에 인증 토큰이 평문으로 들어 있다. 이 문서에는 옮기지 않았다. 별도로 로테이션과 문서 정리가 필요한지 확인해야 한다.
